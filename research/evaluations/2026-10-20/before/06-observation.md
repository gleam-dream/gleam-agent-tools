Two decisive guide lines:
> A library describes what happened; the application attaches metrics, logging, an exporter, or nothing.
> Roar 0.1.0 uses Whisper's older router API and is source-incompatible with the inspected Whisper 0.2.0 API, despite its permissive dependency range.

**Separate the contracts.** Use native BEAM telemetry for optional library observations; Sinal is a candidate typed adapter, subject to availability and compiler/dependency checks. Emit operation measurements and metadata independently of observers. No observer is a valid configuration; business results must not depend on attachment or export success. Do not force consumers to adopt a bus, exporter, JSON, or metrics vendor. One diagnostic may simply be an ordinary log.

Use ephemeral pub/sub for the two panels' entity-invalidation hints. Whisper 0.2 is a candidate for a qualified local target, not yet an installation recommendation. Keep the entity in an authoritative store. Missed/coalesced hints are acceptable because panels reread on notification and mount/reconnect (with a periodic or explicit refresh path if eventual freshness matters). If both panels are children of one coordinator, have it reread once and pass the entity to both; direct callbacks or subjects are simpler when one known owner needs notification. Browser panels in one JavaScript realm differ from browser clients reached through BEAM: the latter need an explicit transport; a BEAM bus does not reach browsers by itself.

Required payments use a payment service and durable ledger/queue or outbox with acknowledged admission. Preserve an existing suitable queue. Grind is conditional on PostgreSQL/OTP fitting the service, not a mandatory addition. Payment-provider idempotency and reconciliation are required because persistence alone cannot make an external charge exactly once. Cluster hints remain a separate lossy notification channel. Reject the proposed universal bus and reject Roar 0.1.0 plus Whisper 0.2.0 until a normally resolved, compiled compatible pair exists. Do not guess a downgrade.

**Consumer path — design pseudocode, not runnable package APIs.** Define native `EntityId`, `OperationError`, and a static `OperationCompleted` event with duration/outcome measurements and correlation/entity metadata. The application composes ordinary configuration values with an operation's typed storage callback; observation does not replace `Result(Entity, OperationError)`. At startup it optionally attaches metrics, structured logs, or both. An ordinary `library.update(entity_id, change, configured_storage)` commits its work, emits the observation, and returns its domain result. The application publishes `EntityChanged(entity_id, revision)` after successful commit. A panel's bounded subscriber rereads the entity and ignores stale read responses using a revision/request token. No observer branch or event-map conversion is required in the library call.

For a payment request, the application validates a native command containing payment ID, amount in minor units, currency, and provider idempotency key; it atomically stores the business intent and durable work where possible. Admission returns a structured accepted/failed/unknown outcome. A worker calls the provider, persists the outcome, and only then emits diagnostic telemetry and refresh hints. Lost admission replies reconcile with the same command/key; unknown provider outcomes are investigated, not blindly replayed.

**Owners and overload.** The application supervisor owns telemetry exporter/forwarder processes, startup routes, and stable handler registrations; it retains attachment handles and detaches on shutdown/reconfiguration. Library calls do not start per-call exporter infrastructure. Keep inline telemetry handlers short because they execute synchronously; route slow exports through an application-owned bounded supervised forwarder. Capacity includes queued and executing events; overload/unavailability drops and counts observations without inline retry. Shutdown loss is acceptable; a drain guarantee must be explicit. Exporter failures must remain diagnostic failures.

The panel/coordinator owns subscription cancellation at unmount, and the application owns topic creation/closure. Use one trusted topic name and one payload contract, not a topic per arbitrary input. Bounded subscription buffers drop old hints; buffer bounds do not bound every mailbox or global memory. Empty and closed are distinct. Keep callbacks short: JavaScript callbacks may run inside publish and BEAM callbacks inside the topic server. Avoid closing/recreating names while stale handles exist. Durable payment runtime/database pools and workers belong to the service supervisor, with migrations and recovery owned operationally; its overload policy rejects/defer admission or persists backlog under explicit limits, never silently drops payments.

**Verification and missing requirements.** Check actual source versions, targets, public APIs, normal resolution and compilation before installation claims. Sinal and Grind are described as unreleased; availability is uncertain. Qualify no-observer operation, callback failure/removal, bounded-forwarder loss, and topic lifecycle. Roar requires distributed disconnect/reconnect, duplicate, cleanup, and atom-allocation checks; trusted finite scopes are not authorization. Determine panel topology, acceptable refresh delay, payment ledger/provider contract, persistence stack, cluster topology, and operational recovery owner before final selection. No build or live-service call is warranted for this synthetic scenario.

# VERIFIED

The split stands; qualification of the proposed packages remains incomplete.

- [Native telemetry 1.4.2](https://telemetry.hexdocs.pm/1.4.2/telemetry.html#attach/4) confirms synchronous execution in the dispatching process, unspecified handler order, removal after callback failure, and unique attachment IDs. This supports the application-owned bounded exporter, rather than network I/O inside library emitters. Monitor handler failures and restore registrations only after fixing the cause.
- Local primary source confirms Sinal's typed public path: define `sinal.event(name, measurement_fields, metadata_fields)`, retain the attachment returned by `sinal.observe`, emit using `sinal.emit(event, measurements, metadata)`, and detach it. See `/code/gleam-dream/sinal/src/sinal.gleam:98`, `:140`, `:202`. Its module documentation says emitting without the telemetry application reaches no handler; attaching starts that application.
- **Amendment to failure isolation:** no observers does not mean arbitrary instrumentation cannot fail. Sinal explicitly permits custom getters/encoders to raise before dispatch (`/code/gleam-dream/sinal/src/sinal.gleam:139`); untrappable termination can kill the executing process. Use trusted total encoding, and do not claim absolute isolation. Registration/startup failures also need handling at application startup. For an actual Erlang-source library, native `telemetry:execute/3` is the ordinary emitter; Sinal is optional for Gleam consumers, not a required language migration.
- `/code/gleam-dream/sinal/src/sinal/forwarder.gleam:33` documents refusal without retries or inline fallback, default capacity 1,024 including executing work, and loss on shutdown (`:48`). `new`/`with_capacity` configure a value before `supervised` starts it (`:206`, `:212`, `:218`). `/code/gleam-dream/sinal/gleam.toml:4` and `:17` confirm compiler >=1.18 and telemetry >=1.4.2,<2. These local files do not establish published availability or equivalence to the guide's pinned revision.

Its publish documentation qualifies dropping by platform; implementation-specific overflow, links, and callback execution remain guide-derived until source inspection succeeds. Handle topic-creation errors explicitly at startup; do not use an unconditional assertion in production recovery logic.

Its specific incompatibility, atom, bridge-cleanup, and distribution assertions remain guide evidence, not independently reproduced findings.
